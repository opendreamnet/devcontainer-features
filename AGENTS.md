# Agent Instructions

## Purpose and Structure

This repository maintains the Dev Container Features OpenDreamnet needs for its development environments. Features are self-contained installation and configuration units published at `ghcr.io/opendreamnet/devcontainer-features/<id>`.

- `src/<id>/`: feature implementation and metadata.
- `test/<id>/`: default tests and integration scenarios.
- `.github/workflows/`: publishing and documentation generation.
- `.devcontainer/`: the environment for developing and testing this collection.

Use `src/tatr` and `test/tatr` as structural references, not as a universal dependency list. Preserve others' changes and keep modifications within the requested scope.

## Adding a Feature

1. Identify the tool, its installation method, licenses, and genuinely supported platforms. Review upstream and the [official features](https://github.com/devcontainers/features/tree/main/src) before choosing an implementation.
2. Create `src/<id>/devcontainer-feature.json` with an `id` matching the directory, an initial semantic version of `1.0.0`, a name, description, documentation/license URLs, and necessary options. The feature version is independent of the tool version.
3. Create `src/<id>/install.sh` following the installation rules below. Options arrive as uppercase environment variables: `tatrVersion` becomes `TATRVERSION`, not `TATR_VERSION`.
4. Create `test/<id>/test.sh`. Use `dev-container-features-test-lib`, `check` assertions, and `reportResults`; verify that the tool is on PATH and works, not just that a file exists.
5. Add `test/<id>/scenarios.json` and one `<scenario>.sh` per scenario. Test the declared distributions, minimal images, defaults, and relevant options, including a pinned version.
6. Run validation and tests. Update the `README.md` catalog and describe what was verified and any limitations. Do not create per-feature workflows if the existing ones already cover publishing.

## Installation Rules

- Prefer `/bin/sh` and `set -eu` when Bash is not needed. Do not assume minimal images include Bash; if it is essential, install it before using it.
- Use brief comments to separate sections and explain non-obvious decisions. Keep code and comments in English, as in `tatr`.
- Check privileges and platforms before modifying the image. Validate options before installing packages or downloading files; never evaluate option values as code.
- Detect package managers by availability where appropriate. Install only necessary dependencies, noninteractively, and clean caches. Do not require support for every package manager if upstream does not allow it.
- Do not replace preinstalled packages unnecessarily. Rocky Minimal may provide `install` through `coreutils-single`; installing `coreutils` indiscriminately causes conflicts.
- Account for aliases and platform-specific dependencies: Photon exposes `yum` as an alias of `tdnf`; prioritize `tdnf` and, when compiling C, include `binutils` and `linux-api-headers` alongside GCC and libc.
- On Arch, do not refresh package databases without a full upgrade. Explain the effect of `pacman -Syu`; avoid upgrading the entire image by default on other distributions.
- Use `mktemp -d` and traps to clean temporary files on success, failure, and interruption. Install commands in `/usr/local/bin` with permissions `0755` and verify that they run.
- When building from source, pin the revision or allow it to be pinned. `tatr` retains this approach to use the native compiler and libc without relying on prebuilt assets.
- When downloading binaries, check architecture and ABI compatibility, including musl/glibc differences. Download over HTTPS, reject HTTP errors, and verify available checksums or signatures before execution; never silently skip verification.
- Add options only when they address a concrete need. Provide safe defaults and clear errors. An option to skip dependencies requires tool validation; upstream tests must be optional and compatible with the selected revision.

## Validation

From the repository root, replace `tatr` with the new identifier:

```sh
sh -n src/tatr/install.sh
devcontainer features test --project-folder . --features tatr --skip-duplicated
devcontainer features test --project-folder . --features tatr --skip-autogenerated --skip-duplicated --filter alpine
```

- Use `bash -n` if the installer requires Bash. Run ShellCheck when available and validate JSON files.
- Cover invalid configuration, missing privileges/dependencies, and unsupported platforms without performing actual installations on the host.
- The test library requires Bash: on Alpine, `alpine.sh` installs it after the feature is built. Do not add Bash to the installer solely to satisfy the test harness.
- Check every declared platform and architecture. Do not infer compatibility from package manager detection or report unexecuted tests as passing. Initial `tatr` validation was performed on `x86_64`.
- Current workflows publish features and generate documentation, but do not run tests. Validate before publishing, and do not commit, push, or publish unless explicitly requested.

## Maintenance

Bump the feature version according to SemVer when changing behavior or options; preserve compatibility with existing configurations unless making intentional breaking changes in a major release. Use metadata as the source of truth for options and generated per-feature documentation; do not manually edit those generated READMEs. Do not include secrets or change the licenses of installed tools.
